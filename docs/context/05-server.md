# Сервер: API, бот, cron, синхронизация

_Область: server/ — Cloudflare Worker: API, авторизация Telegram, протокол /api/sync, cron, бот grammY, D1 + R2_

Серверная часть — один Cloudflare Worker (`server/src/index.ts`), который совмещает четыре роли: REST-API мини-приложения под `/api/*`, приёмник вебхука Telegram под `/bot/:secret`, минутный cron и раздачу статики фронта через биндинг ASSETS. Данные лежат в D1 (пять синхронизируемых таблиц + служебная `sent_notifications`), байты голосовых — в R2. Синхронизация — офлайн-first pull/push одним POST `/api/sync`: клиент шлёт свой outbox и курсор `since`, сервер применяет last-write-wins по клиентскому `updatedAt` и отдаёт всё, что изменилось по серверной метке `synced_at`, плюс новый курсор `now`, заведомо сдвинутый на 60 с назад. Клиенту не доверяют ничему, кроме содержимого его собственных строк: `user_id` всегда берётся из подписанного initData, идентификаторы строк переписываются или проверяются на сервере, серверные колонки (`r2_key`, `uploaded_at`, `tg_file_id`) физически исключены из upsert-конвертера. Вся работа с Telegram построена вокруг одного инварианта — вебхук никогда не отвечает ошибкой и любой повторно доставленный апдейт не должен создавать дубликат, отсюда детерминированные id, UNIQUE-индекс по `tg_file_unique_id` и `waitUntil` для долгих операций. Почти все нетривиальные решения снабжены комментариями с обоснованием прямо в коде, а история коммитов (2c1efcc, b23c6da, 2d787bf, a323b66) фиксирует, какой именно сбой каждое из них закрывает.

## Решения (36)

### Один воркер: API, бот, cron, статика

**Что сделано.** Hono-приложение отдаёт `/api/*`, принимает вебхук на `/bot/:secret`, экспортирует `scheduled()` для cron, а всё остальное отдаёт в биндинг ASSETS с SPA-фолбэком; в wrangler.toml `run_worker_first` явно перечисляет `/api/*` и `/bot/*`.

**Почему.** Не задокументировано, вывод из кода: одна деплой-единица на бесплатном тарифе Cloudflare, статика и API на одном origin (отсюда и отсутствие проблем с CORS у мини-приложения), а `run_worker_first` нужен, потому что иначе ассеты перехватили бы эти пути раньше воркера.

**Основание:** `server/src/index.ts:122-129, server/wrangler.toml:6-11` · достоверность: EXTRACTED

### Авторизация: заголовок `tma <initData>`

**Что сделано.** Все `/api/*` проходят через middleware, которое читает `Authorization: tma <initData>`, проверяет HMAC-SHA256 по схеме Telegram (`secretKey = HMAC('WebAppData', BOT_TOKEN)`), требует `auth_date` не старше 48 ч, сравнивает хеш побитово за постоянное время и достаёт `user.id`; иначе 401.

**Почему.** Обоснование схемы — ссылка на документацию Telegram прямо в комментарии (auth.ts:22-25); окно 48 ч и constant-time сравнение появились в коммите 2c1efcc («48h initData window»), чтобы мини-приложение переживало долгую сессию без перелогина и не давало таймингового оракула.

**Основание:** `server/src/auth.ts:26-57, server/src/index.ts:44-57, коммит 2c1efcc` · достоверность: EXTRACTED

### Dev-обход авторизации только на localhost

**Почему.** Задокументировано в комментарии и в wrangler.toml/README: переменная должна жить только в `server/.dev.vars`, а привязка к localhost сделана, чтобы случайный деплой этой переменной не открыл вход кому угодно.

### `/api/health` публичен по порядку регистрации

**Что сделано.** `app.get('/api/health')` зарегистрирован раньше auth-middleware и отвечает `{ok, now}` без авторизации; все маршруты ниже — только после проверки initData.

**Почему.** Не задокументировано, вывод из кода: Hono исполняет совпавшие обработчики в порядке регистрации, health не вызывает `next()`, поэтому middleware до него не доходит. Выглядит намеренным (health-пинг и сверка часов клиента), но комментария об этом нет.

### Ленивое идемпотентное создание пользователя

**Что сделано.** `ensureUser` вызывается на каждом авторизованном запросе и из каждого хендлера бота: обновляет `firstName/username/lastSeen` либо создаёт пользователя и сразу четыре дефолтные категории с детерминированными id `${tgId}:cat:${i}`, всё через `onConflictDoNothing`.

**Почему.** Задокументировано: «Concurrent first requests may race here; deterministic ids + do-nothing conflicts keep it idempotent» — отдельной регистрации нет, первый же запрос из мини-аппа или бота создаёт аккаунт, а гонка двух параллельных первых запросов не должна дублировать категории.

**Основание:** `server/src/sync.ts:41-80` · достоверность: EXTRACTED

### Курсор синхронизации — серверный synced_at

**Что сделано.** У всех пяти таблиц есть колонка `synced_at`, проставляемая сервером в момент приёма; pull делает `synced_at > since`, а не `updated_at > since`. Миграция 0001 добавила колонку и индексы `(user_id, synced_at)`.

**Почему.** Задокументировано в заголовке миграции: «Server-assigned receive timestamp: the pull cursor must not depend on client clocks» — иначе устройство с отстающими часами навсегда пропускало бы чужие правки.

**Основание:** `server/migrations/0001_sync_rev.sql:1-4,12-15, server/src/sync.ts:125-140` · достоверность: EXTRACTED

### Курсор с перекрытием в 60 секунд

**Что сделано.** В ответе возвращается `now = Date.now() - 60_000`, снятое ДО собственных записей запроса; клиент кладёт его в `lastSync`.

**Почему.** Задокументировано: курсор берётся до записей и с запасом, чтобы параллельный запрос или тик cron, проштамповавший строки чуть раньше, но закоммитивший позже, всё равно доехал в следующий раз; повтор безвреден, потому что клиентский merge тоже LWW.

**Основание:** `server/src/sync.ts:30-31,184-186,206, web/src/lib/sync.ts:105` · достоверность: EXTRACTED

### Разрешение конфликта: LWW по updatedAt

**Что сделано.** `upsertLWW` сначала читает существующие строки чанками по 50 id, затем построчно: нет строки — INSERT ... ON CONFLICT DO NOTHING; есть — UPDATE только при строгом `incoming.updatedAt > existing.updatedAt`, WHERE всегда содержит и `id`, и `user_id`. Равные метки проигрывают (побеждает то, что уже в базе).

**Почему.** Чанки по 50 — комментарий «D1 allows at most 100 bound parameters per statement». Само LWW — заявленная модель протокола (docs/voice-notes-contract.md:5-7, README). Построчный, а не батчевый апсерт нигде не обоснован — вывод из кода: нужна индивидуальная проверка версии и хук для задач.

**Основание:** `server/src/sync.ts:28-29,84-123` · достоверность: EXTRACTED

### Клиентские часы обрезаются вперёд

**Что сделано.** `timestamp()` приводит любую метку к диапазону [0, 4102444800000] и дополнительно обрезает по `now + 5 минут`.

**Почему.** Задокументировано: «Clamp fast clocks so a skewed device cannot lock a row for hours» — иначе устройство с часами из будущего выигрывало бы LWW у всех остальных навсегда.

**Основание:** `server/src/validate.ts:78-82` · достоверность: EXTRACTED

### Кривые значения клампятся, а не отвергаются

**Что сделано.** Выход за диапазон у минут задачи, длительности и размера голосовой заметки округляется в границы (`clamp`), а не приводит к 400; ошибку получают только структурно неверные данные (не-число, не-строка, плохая дата, плохой uuid/mime).

**Почему.** Задокументировано и подтверждено коммитом a323b66: часовое аудио из бота проходило валидацию на записи, но падало на обратной валидации — строка попадала в outbox, каждый следующий `/api/sync` отвечал 400, и устройство переставало синхронизироваться вообще, пока не очистишь хранилище.

**Основание:** `server/src/validate.ts:60-64,203-206, коммит a323b66` · достоверность: EXTRACTED

### Исключение из LWW: завершение бьёт авто-перенос

**Что сделано.** Хук в `upsertLWW`: если в базе у задачи статус `moved` (её перенёс cron), а клиент прислал `done`/`cancelled`, запись применяется принудительно, независимо от меток времени, её `updatedAt` поднимается до серверного `syncedAt`, а все живые carry-копии (`${root}:carry:%` со статусом `todo`) помечаются удалёнными.

**Почему.** Задокументировано: пользовательское завершение должно победить синтетический статус на всех устройствах (отсюда подмена метки на серверную), а перенесённая копия обязана исчезнуть, иначе задача задвоится.

**Основание:** `server/src/sync.ts:109-114,168-180` · достоверность: EXTRACTED

### Авто-перенос: детерминированный id копии

**Что сделано.** Cron раз в сутки (после 00:05 локального времени пользователя, если включён `carryover`) берёт неудалённые неповторяющиеся задачи прошлых дат со статусом `todo`/`in_progress`, создаёт копию с id `${carryRootId(id)}:carry:${today}` и ставит оригиналу статус `moved`.

**Почему.** Задокументировано: id выводится из корневой задачи, «чтобы клиент и сервер сошлись, даже если устройство пропустило несколько дней» — повторный перенос той же задачи попадает в тот же id и гасится `onConflictDoNothing`.

**Основание:** `server/src/cron.ts:41-76,96-99` · достоверность: EXTRACTED

### Перенос двигает updatedAt ровно на 1 мс

**Что сделано.** Оригинальной задаче ставится `status='moved', updatedAt = row.updatedAt + 1`.

**Почему.** Задокументировано: «Bump by one millisecond only: any real user edit made later must win last-write-wins» — серверное системное изменение не должно перебивать последующую правку человека.

**Основание:** `server/src/cron.ts:73-74` · достоверность: EXTRACTED

### sent_notifications как универсальный claim

**Что сделано.** Единственный примитив взаимоисключения — `INSERT INTO sent_notifications(key) ON CONFLICT DO NOTHING` с проверкой `meta.changes > 0`. На нём держатся: однократность напоминаний/дайджеста/отчёта, суточный перенос, суточная чистка таблицы, часовой purge R2, а также рейт-лимиты (`export:<uid>:<минута>`, `voicesend:<uid>:<10 с>`). `once()` при ошибке отправки снимает claim, чтобы следующий тик повторил.

**Почему.** Задокументировано как «Atomic one-shot claim: exactly one caller gets `true`». Использование той же таблицы как рейт-лимитера не обосновано — вывод из кода: не хотели заводить KV/Durable Object ради двух счётчиков.

**Основание:** `server/src/cron.ts:20-39, server/src/index.ts:75, server/src/voice.ts:202` · достоверность: EXTRACTED

### Cron ежеминутно, окно допуска 3 минуты

**Что сделано.** Триггер `* * * * *`; событие считается «подошедшим», если `fireAt <= nowMin && fireAt > nowMin - 3`. Пользователи, не заходившие 180 дней, пропускаются целиком; записи claim старше 3 суток чистятся раз в день.

**Почему.** Окно задокументировано как «tolerance window so a missed cron tick still fires»; 180 дней — «recurring reminders keep going for half a year», в коммите b23c6da окно расширено специально для тех, кто пользуется только уведомлениями и не открывает мини-апп.

**Основание:** `server/wrangler.toml:24-25, server/src/cron.ts:10-18,83,86-88, коммит b23c6da` · достоверность: EXTRACTED

### Перенос работает без токена бота

**Что сделано.** `runCron` создаёт бота только при наличии `BOT_TOKEN`; блок авто-переноса выполняется до проверки `if (!bot) continue`.

**Почему.** Задокументировано: «Carry-over must run even when the bot is not configured; only messaging needs the token» — данные пользователя не должны зависеть от того, настроен ли канал уведомлений.

**Основание:** `server/src/cron.ts:80-81,96-101` · достоверность: EXTRACTED

### Вебхук: секрет в пути плюс secret_token

**Что сделано.** `POST /bot/:secret` сравнивает параметр пути с `WEBHOOK_SECRET` за постоянное время, а заголовок `X-Telegram-Bot-Api-Secret-Token` проверяет только если он вообще прислан. `setup-bot.mjs` регистрирует URL с секретом в пути, тот же секрет как `secret_token`, `allowed_updates: [message, callback_query]` и `drop_pending_updates: true`.

**Почему.** Двойная проверка задокументирована комментарием. Почему заголовок необязателен — не задокументировано, вывод из кода: терпимость к вебхуку, зарегистрированному без `secret_token`, и к ретраям без заголовка; фактическая защита при этом держится на секрете в URL.

**Основание:** `server/src/index.ts:20-25,100-103, server/scripts/setup-bot.mjs:83-88` · достоверность: EXTRACTED

### Вебхук никогда не отвечает 5xx

**Что сделано.** Три слоя: `bot.catch` логирует ошибку хендлера; `try/catch` вокруг `webhookCallback` отвечает `ok` даже на исключение; бот создаётся с фиктивным `botInfo` (id из токена), а настоящий `getMe` подтягивается в фоне.

**Почему.** Задокументировано в коде и в коммите 2d787bf: grammY отдаёт ошибки в `bot.catch` только при long polling, а на вебхуке они всплывали как 500, и Telegram часами переотправлял тот же апдейт, повторяя каждый побочный эффект; `getMe` перед первым апдейтом каждого изолята давал ровно ту же петлю при сетевом сбое или 429.

**Основание:** `server/src/index.ts:112-119, server/src/bot.ts:195-228,233-236, коммит 2d787bf` · достоверность: EXTRACTED

### Долгие операции уезжают в waitUntil

**Что сделано.** Роут вебхука кладёт `c.executionCtx.waitUntil` в модульную переменную через `setWaitUntil`, хендлер голосового читает её ДО первого `await` и запускает импорт фоном; без контекста (тесты) задача просто ожидается.

**Почему.** Задокументировано: `getBot` кеширован на изолят, поэтому хендлеры не могут замкнуться на ExecutionContext конкретного запроса; а импорт (скачивание файла из Telegram + запись в R2) обязан пережить ответ вебхука, иначе Telegram переотправит апдейт. Чтение до первого await — защита от подмены модульной переменной параллельным запросом.

**Основание:** `server/src/index.ts:104-111, server/src/bot.ts:82-104,360-362,402` · достоверность: EXTRACTED

### Повторный апдейт не создаёт дубликат

**Что сделано.** Быстрая задача из текста получает id `${userId}:tg:${message_id}` и вставляется с `onConflictDoNothing`. Голосовое дедуплицируется по `(user_id, tg_file_unique_id)`: сначала SELECT, затем UNIQUE-индекс как последний рубеж — проигравший гонку удаляет свой объект из R2 и возвращает строку победителя.

**Почему.** Задокументировано: «Id derived from the update so a redelivered update cannot create a duplicate» и «Lost the race against a redelivered update: keep the winner's row, drop our orphan object». Это ответ на ту же проблему переотправки, что и слой обработки ошибок.

**Основание:** `server/src/bot.ts:324-348, server/src/voice.ts:276-282,323-334, server/migrations/0002_voice.sql:24` · достоверность: EXTRACTED

### Бот работает только в личном чате

**Что сделано.** Быстрое добавление задачи и приём голосовых отключены вне `chat.type === 'private'`; `/start` в группе отвечает текстом `privateOnly`; web-app-кнопка подставляется тоже только в приватном чате.

**Почему.** Задокументировано: «group chats would create tasks and collide on message ids» — id задачи строится из `message_id`, который уникален лишь в пределах чата.

**Основание:** `server/src/bot.ts:246-247,253-256,291-292,365` · достоверность: EXTRACTED

### Категория по #тегу матчится в JS

**Что сделано.** Все живые категории пользователя выбираются из D1, а сравнение имени с `#тег` делается в JavaScript по `toLowerCase()`.

**Почему.** Задокументировано и подтверждено коммитом 2d787bf: `lower()` в SQLite работает только с ASCII, поэтому `#здоровье` никогда не совпадало с категорией «Здоровье».

**Основание:** `server/src/bot.ts:308-320, коммит 2d787bf` · достоверность: EXTRACTED

### HTML-сообщения режутся без разрыва тегов

**Что сделано.** Все исходящие сообщения идут с `parse_mode: 'HTML'`; `esc()` обрезает до 200 символов и экранирует `&<>`, `truncateMessage()` режет на 4000 символах, выбрасывает оборванное начало тега и дозакрывает `code/b/i`.

**Почему.** Задокументировано: Telegram отвергает сообщения длиннее 4096 символов, а обрезанная разметка ломает парсинг и весь ответ теряется; поведение закреплено тестами.

**Основание:** `server/src/bot.ts:144-159, server/src/voice.test.ts:60-75` · достоверность: EXTRACTED

### Callback-кнопки правки голосовой

**Что сделано.** Данные кнопки — `v:<uuid>:<m|e|y|t|d>` (секция, ±день, удаление), матчатся регуляркой, строка правится только по паре `(id, user_id)`, патч всегда содержит `updatedAt = now` и `syncedAt = now`; на удалённой строке бот отвечает «удалено» и правит текст сообщения.

**Почему.** Формат задокументирован ограничением Telegram в 64 байта на callback_data (закреплено тестом). Подъём `updatedAt` здесь намеренный, в отличие от серверных операций: это правка пользователя, и она должна выиграть LWW на устройствах.

**Основание:** `server/src/bot.ts:80,106-115,408-456, server/src/voice.test.ts:31-50` · достоверность: EXTRACTED

### Граница доверия: user_id только из initData

**Что сделано.** Валидаторы принудительно ставят `userId: 0`, реальный id подставляется конвертерами `*ToRow(x, userId)` из авторизованного пользователя; id заметки дня переписывается в `${userId}:${date}`, id вхождения — в `${taskId}:${date}`; ключ R2 — `voice/${userId}/${id}` при строгой проверке uuid по `ID_RE`.

**Почему.** Скоупинг ключа R2 и отказ от «сбегающих» id закреплены тестом «object keys are scoped per user and ids are strictly validated». Для id заметки обоснование не записано — вывод из кода: без префикса `userId` одна дата была бы глобальным первичным ключом и заметки разных пользователей столкнулись бы.

**Основание:** `server/src/validate.ts:118,144,177, server/src/db/schema.ts:207, server/src/voice.ts:17,26, server/src/voice.test.ts:86-93` · достоверность: EXTRACTED

### Граница доверия: серверные колонки вне sync

**Что сделано.** `voiceToRow` возвращает только клиентские колонки, поэтому апсерт из `/api/sync` физически не может обнулить `r2_key`, `uploaded_at`, `tg_file_id`, `tg_file_unique_id`; `validateVoiceNote` принудительно ставит `uploadedAt: null`; `voiceFromRow` отдаёт клиенту из серверных полей только `uploadedAt`.

**Почему.** Задокументировано в комментариях к обеим функциям и в контракте: серверные изменения этих колонок меняют только `synced_at` и никогда `updated_at`, иначе параллельное удаление с клиента проиграло бы гонку.

**Основание:** `server/src/db/schema.ts:86-91,216-250, server/src/validate.ts:212-213, docs/voice-notes-contract.md:67-80` · достоверность: EXTRACTED

### Настройки — белый список полей

### Лимиты полезной нагрузки на двух уровнях

**Что сделано.** Транспортный лимит: `bodyLimit` 1 МБ на `/api/sync` и `/api/export/*`, отдельный `VOICE_MAX_BYTES` (25 МБ) на PUT блоба. Логический: максимум 500 строк на таблицу за запрос, обрезка длин (title 500, description/note 20 000, checklist 100 позиций и т. д.). Клиент шлёт страницами по 200.

**Почему.** Разделение задокументировано комментарием «JSON routes only: voice blobs carry their own limit» — глобальный лимит в 1 МБ убил бы загрузку голосовых. Порог в 500 строк проговорен и на клиенте («The server accepts at most 500 rows per table per request; keep well under it»).

### Единый обработчик ошибок сохраняет статусы

**Что сделано.** `app.onError`: `ValidationError` → 400 с текстом поля, `HTTPException` отдаёт собственный ответ (в частности 413 от `bodyLimit`), всё прочее логируется и превращается в 500 `{error:'internal'}`.

### R2 — необязательная зависимость

**Что сделано.** Биндинг `VOICE` объявлен опциональным в типе Env: без него метаданные голосовых продолжают синхронизироваться, PUT блоба отвечает 503 `{error:'storage'}`, GET — 404, импорт из бота возвращает `reason:'storage'`, а cron-purge молча выходит.

**Почему.** Задокументировано в комментарии к Env и в README: R2 может требовать привязки карты даже на бесплатном тарифе, поэтому пользователь вправе удалить блок `[[r2_buckets]]`, и остальное приложение обязано работать.

**Основание:** `server/src/env.ts:4-5, server/src/voice.ts:121,155,283,343, README.md (раздел «R2»)` · достоверность: EXTRACTED

### PUT блоба сам создаёт строку метаданных

**Что сделано.** Если строки нет, она создаётся из query-параметров (`date`, `section`, `duration`, `createdAt`, `peaks`) через тот же `validateVoiceNote` с принудительным `source='app'`, после чего строка перечитывается из базы. Повторный PUT при уже выставленном `uploaded_at` возвращает 200 с заметкой без записи; при `deleted_at` — 410.

**Почему.** Задокументировано: загрузка «никогда не зависит от того, доехал ли раньше дебаунсированный /api/sync», а перечитывание вместо доверия собственному INSERT — потому что параллельный `/api/sync` мог создать строку первым.

**Основание:** `server/src/voice.ts:91-120, docs/voice-notes-contract.md:94-104` · достоверность: EXTRACTED

### GET блоба: Range и само-лечение

**Что сделано.** Заголовки отдаются в R2 только если клиент реально прислал `Range` (иначе 206 приходил бы на каждое скачивание); ошибка R2 на неудовлетворимом диапазоне превращается в 416 с `Content-Range: bytes */size`; если объекта нет, строке обнуляются `r2_key`/`uploaded_at` с новым `synced_at` и возвращается 404. Ответ помечен `private, no-store` и `nosniff`.

**Почему.** Оба поведения задокументированы комментариями: некоторые рантаймы сообщают «полный» диапазон при его отсутствии, а забытый ключ нужно погасить, «чтобы клиенты перестали его просить» — иначе устройство бесконечно ретраит скачивание удалённого purge-ом объекта.

**Основание:** `server/src/voice.ts:54-60,148-191` · достоверность: EXTRACTED

### Отправка голоса в чат с деградацией

**Что сделано.** POST `/api/voice/:id/send` при наличии `tg_file_id` пробует `sendVoice` → `sendAudio` → `sendDocument`, откатываясь только на ошибке Telegram 400; при наличии блоба в R2 — `sendVoice` для m4a/ogg/mp3 с откатом в документ, webm сразу документом. 403 → 409 `write_access`, 429 → 429 с `retryAfter`, прочее → 502.

**Почему.** Задокументировано: «A file_id keeps its Telegram type», поэтому заранее неизвестно, каким методом файл примут; `InputFile` расходуется одним запросом, отсюда фабрика `file()` для повторной попытки.

**Основание:** `server/src/voice.ts:194-257` · достоверность: EXTRACTED

### Отложенная чистка R2, томбстоуны остаются

**Что сделано.** Раз в час (claim по часу) удаляются объекты R2 для заметок, помеченных удалёнными более суток назад, пачками до 500; сами строки-томбстоуны сохраняются, у них лишь обнуляются `r2_key`/`uploaded_at` и обновляется `synced_at`.

**Почему.** Задокументировано: «the undo window is long gone» для суток отсрочки и «the tombstones themselves stay for sync» — томбстоун обязан дожить до всех устройств, иначе они восстановят удалённую заметку.

**Основание:** `server/src/cron.ts:151-158, server/src/voice.ts:341-359` · достоверность: EXTRACTED

### Экспорт заметок документом в чат

**Что сделано.** POST `/api/export/notes` собирает все непустые заметки дня в Markdown и шлёт файлом в личный чат пользователя через бота; рейт-лимит — один вызов в минуту через claim, без токена бота 503, при нуле заметок `{ok:true,count:0}` без отправки.

## Открытые вопросы (7)

- Pull не пагинирован: при `since = 0` (новое или очищенное устройство) сервер отдаёт ВСЕ строки пользователя одним ответом, без лимита и без курсора продолжения — push ограничен 500 строками на таблицу, а ответ ничем (server/src/sync.ts:125-140). Насколько это безопасно при многолетней истории и лимитах D1/размера ответа — не проверено и нигде не оговорено.
- Апсерт выполняется построчно, вне транзакции и без batch: каждая строка входящего пакета — отдельный SELECT-чанк плюс INSERT или UPDATE (server/src/sync.ts:95-122). Полусинхронизированный результат при обрыве посреди запроса возможен; протокол переживает это за счёт повторной отправки outbox, но явного обоснования отказа от `db.batch` в коде нет.
- Cron каждую минуту выбирает всех пользователей, активных за 180 дней, и делает на каждого минимум два запроса к D1 плюс по запросу на claim (server/src/cron.ts:83,90-106). Ни пагинации, ни ограничения по времени тика нет — поведение при росте базы не проверено.
- Проверка `X-Telegram-Bot-Api-Secret-Token` пропускается, если заголовка нет (server/src/index.ts:102-103). Не задокументировано, осознанная ли это уступка (вебхук, зарегистрированный без secret_token) или недосмотр: фактически защита сводится к секрету в пути URL, который попадает в логи прокси.
- `ensureUser` на гонке первых запросов возвращает собранный в памяти `row`, даже если INSERT проиграл конфликт (server/src/sync.ts:63,79) — тогда ответ отдаст дефолтные настройки вместо уже сохранённых. Окно узкое (только самый первый запрос), но код это не оговаривает.
- Окно initData проверяется по модулю: `Math.abs(now/1000 - auth_date) > 48ч` (server/src/auth.ts:34), то есть метка из будущего до 48 часов тоже принимается. Обоснование не записано.
- Идентификатор вхождения `${taskId}:${date}` не содержит user_id (server/src/validate.ts:144). Перезаписать чужую строку нельзя — UPDATE скоупится по user_id, а INSERT гасится `onConflictDoNothing`, — но при коллизии id правка отправителя молча исчезнет без ответа об ошибке. Намеренно ли это, из кода не следует.
